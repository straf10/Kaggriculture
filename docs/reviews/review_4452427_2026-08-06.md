### C1 — Το holdout «κάηκε»: το v1c GO προήλθε από δεύτερο τράβηγμα μετά από tuning πάνω στο ίδιο holdout  [CONFIRMED-EXEC]

**Περιγραφή.** Η ακολουθία των artefacts στο `runs/` δείχνει καθαρά:

| Σειρά | Run | fingerprint(agent_a) | stage | verdict | mean_diff | GO |
|---|---|---|---|---|---:|---|
| 1 | `gate_v1c_dev2` | `404c84…` | dev-screen | NON_INFERIOR | −597.1 | False |
| 2 | `gate_v1c_holdout` | `404c84…` | **holdout-confirm** | **INCONCLUSIVE** | −690.8 | False |
| 3 | `gate_v1c_carrot3_subset` | `75baff…` | — | NON_INFERIOR | −340.0 | False |
| 4 | `gate_v1c_dev3` | `75baff…` | dev-screen | NON_INFERIOR | −305.6 | False |
| 5 | `gate_v1c_holdout2` | `75baff…` | **holdout-confirm** | NON_INFERIOR | −297.0 | **True** |

Τα βήματα 2 και 5 τρέχουν στο **ίδιο ακριβώς seed set** (`100–147`, επαληθεύτηκε από τα `per_seed`

> INCONCLUSIVE, narrowly missing NON_INFERIOR … **3 was the smallest bump that cleared

Δηλαδή η επιλογή της τιμής `3` έγινε **με κριτήριο το holdout αποτέλεσμα**. Αυτό παραβιάζει και τους
δύο ρητούς κανόνες:

`gate_v1e_holdout_final` (fp `f0ad48…`, GO=True) — δύο holdout τραβήγματα, με αλλαγή κώδικα ανάμεσα.

### C2 — Το `stage="holdout-confirm"` δεν επαληθεύεται ποτέ έναντι των seeds· ένα dev-screen run μπορεί να παράγει `GO=True`  [CONFIRMED-READ]

**Περιγραφή.** Δύο ξεχωριστές τρύπες στο ίδιο σημείο:

**(α) Καμία διασταύρωση stage ↔ seeds.** Το [harness/compare.py:160-161](harness/compare.py#L160-L161)
επικυρώνει μόνο ότι το `stage` ανήκει στο `VALID_STAGES`. Δεν υπάρχει πουθενά έλεγχος ότι τα seeds
ενός `holdout-confirm` είναι όντως τα `HOLDOUT_SEEDS` — η `compare.py` δεν κάνει καν import το
`harness.seeds`. Στο [harness/cli.py:66](harness/cli.py#L66):

```python
stage = args.stage if args.stage is not None else _STAGE_BY_SEED_SET.get(args.seed_set)
```

το ρητό `--stage` **υπερισχύει** του `--seed-set` χωρίς καμία προειδοποίηση. Άρα:

```
python -m harness.cli compare A B --seed-set dev --stage holdout-confirm --metrics
```

δίνει `GO=True` από τα **dev seeds πάνω στα οποία έγινε το tuning**. Ολόκληρη η ασφάλεια του §1.5.3
είναι παρακάμψιμη από έναν συνδυασμό flags που δεν βγάζει ούτε warning.

**(β) Καμία επιβολή του «exactly once».** Το docstring του `compare()` ισχυρίζεται «only
holdout-confirm, **checked exactly once**, can be [a GO]», αλλά κανένα state δεν κρατιέται πουθενά:
ούτε ledger αρχείο, ούτε έλεγχος για προϋπάρχον `runs/*/results.json` με ίδιο `code_fingerprints[1]`
και `stage="holdout-confirm"`. Το C1 είναι η άμεση συνέπεια αυτού.

**Impact.** Το κεντρικό control του πρωτοκόλλου μέτρησης είναι διακοσμητικό. Ένα λάθος flag ή μια
βιαστική επανάληψη αρκεί για ψεύτικο GO, και το `results.json` δεν αφήνει κανένα ίχνος ότι κάτι
πήγε στραβά — φαίνεται πανομοιότυπο με ένα νόμιμο GO.

**Οδηγίες επίλυσης.**
1. Στο `compare()`, import `HOLDOUT_SEEDS` και:
   ```python
   if stage == "holdout-confirm" and not set(seeds) <= set(HOLDOUT_SEEDS):
       raise ValueError(...)   # όχι warning — raise
   if stage == "dev-screen" and not set(seeds) <= set(DEV_SEEDS):
       raise ValueError(...)
   ```
   Αν χρειαστεί δεύτερο confirm σετ (C1), πρόσθεσέ το στο `seeds.py` και επίτρεψε union.
2. Πρόσθεσε **confirm ledger**: ένα tracked `checkpoints/confirm_log.jsonl` με
   `{timestamp, agent_a_fp, agent_b_fp, seed_set_name, verdict, go}`. Το `compare(stage=
   "holdout-confirm")` γράφει μια γραμμή· αν υπάρχει ήδη γραμμή για το ίδιο `(agent_b_fp,
   seed_set_name)`, **raise** εκτός αν περαστεί ρητά `allow_repeat_confirm=True` (που να καταγράφεται
   στο `results.json` ως πεδίο `repeat_confirm_index: N`, ώστε ένα δεύτερο τράβηγμα να είναι πάντα
   ορατό στο ίδιο το artefact).
3. Στο CLI, αν δοθούν και `--stage` και `--seed-set` και δεν ταιριάζουν, `parser.error()`.
4. Test: `test_compare_rejects_holdout_stage_on_dev_seeds`, `test_compare_second_confirm_raises`.

**Effort:** 1.5–2 ώρες μαζί με tests.

### C3 — Το `--resume` μπορεί να «ξεπλύνει» ένα ΑΜΕΤΡΗΤΟ metric gate σε `metric_gate_passed=True` → `GO=True`  [CONFIRMED-READ]

**Περιγραφή.** Το `_finalize()` γράφει **πάντα** τα τέσσερα metric πεδία, ακόμη κι όταν το run έγινε
με `metrics=False`, γιατί χρησιμοποιεί `o.get(..., 0)`:

```python

"water_weeds_lost_a": sum(o.get("water_weeds_lost_a", 0) for o in orientations),
"animals_escaped_a":  sum(o.get("animals_escaped_a", 0) for o in orientations),
```

Άρα ένα `metrics=False` run αφήνει στο `results.jsonl` σειρές με **μηδενικά που σημαίνουν «δεν
μετρήθηκε»**, όχι «μετρήθηκε και ήταν 0». Στη συνέχεια το resume meta line
([compare.py:209-212](harness/compare.py#L209-L212)) καταγράφει **μόνο** `code_fingerprints` — όχι
`metrics`, όχι `both_seats`, όχι `steps`. Οπότε:

```
python -m harness.cli compare A B --seed-set holdout --out runs/g          # χωρίς --metrics
python -m harness.cli compare A B --seed-set holdout --out runs/g --resume --metrics
```

Το δεύτερο run βρίσκει και τα 48 seeds ήδη «done», δεν παίζει **κανένα** episode, αθροίζει τα
ψευδο-μηδενικά στη [compare.py:438-441](harness/compare.py#L438-L441), θέτει
`metric_gate_passed=True` (γιατί `metrics=True` σαν παράμετρος) και `go=True`. Το `results.json` που
βγαίνει είναι δυσδιάκριτο από ένα γνήσιο GO.

Το ίδιο ισχύει για `both_seats`: resume ενός `--single-seat` run μέσα σε ένα both-seats gate αναμιγνύει
1-orientation και 2-orientation seeds σε ένα `mean_diff` που φαίνεται πλήρες.

**Impact.** Ακριβώς το σενάριο που το §1.5.3 έγραψε για να αποκλείσει («ένα unmeasured metric gate
δεν πρέπει ποτέ να μετράει σιωπηλά ως passed»), παρακάμπτεται από ένα flag. **Κανένα υπάρχον
αποτέλεσμα δεν επηρεάζεται** — κανένα `runs/gate_*` δεν χρησιμοποίησε `--resume` (επαληθεύτηκε: όλα
τα `results.jsonl` έχουν ένα ενιαίο meta line και συνεχόμενα seeds). Είναι λανθάνον, όχι ενεργό.

**Οδηγίες επίλυσης.**
1. Βάλε στο meta line ολόκληρο το «run contract»:
   `{"_meta": True, "code_fingerprints": [...], "metrics": bool, "both_seats": bool, "steps": steps|None, "seeds_requested": [...]}`
   και στο resume **raise** αν οποιοδήποτε από αυτά διαφέρει, με το ίδιο μήνυμα στυλ όπως ήδη κάνει
   για τα fingerprints (review.md M2 του προηγούμενου review — το pattern υπάρχει, απλά δεν
   επεκτάθηκε στα νέα πεδία).
2. Εναλλακτικά/επιπλέον: γράψε τα metric πεδία ως `None` (όχι `0`) όταν `metrics=False`, και κάνε το

## 2. HIGH

### H1 — Το `min_effect` / non-inferiority margin δεν καταγράφεται πουθενά, και **μεγαλώνει** όσο βελτιώνεται ο agent  [CONFIRMED-EXEC]

Το [compare.py:383-391](harness/compare.py#L383-L391) υπολογίζει
`effective_min_effect = max(200, 0.02 × mean(bank_b))` και το χρησιμοποιεί για **και τα τρία**
κατώφλια (IMPROVED, REGRESSED, NON_INFERIOR) — αλλά **δεν το βάζει στο `CompareResult`**, άρα δεν
υπάρχει ούτε στο `results.json` ούτε στο CLI output. Ανακατασκευάζοντάς το από τα `per_seed` rows:

| Gate | mean(bank_b) | margin | mean_diff | verdict |
|---|---:|---:|---:|---|
| `gate_v1d_holdout` (vs v1b) | $20.282 | **$406** | +18.667 | IMPROVED |
| `gate_v1c_holdout2` (vs v1d) | $38.657 | **$773** | −297 | NON_INFERIOR |
| `gate_v1e_holdout_final` (vs v1c) | $38.031 | **$761** | +1.499 | IMPROVED |

**Impact.** (α) Κανείς που διαβάζει ένα `results.json` δεν μπορεί να πει έναντι ποιου κατωφλίου
κρίθηκε το verdict — το ίδιο `mean_diff=-500` είναι NON_INFERIOR σε ένα gate και REGRESSED σε άλλο,
χωρίς κανένα ορατό ίχνος του γιατί. (β) Πιο σοβαρό: το margin **αυτο-χαλαρώνει**. Καθώς το bank
τριπλασιάστηκε από $20k σε $39k, η ανοχή σχεδόν διπλασιάστηκε ($406 → $773). Κάθε επόμενο increment
επιτρέπεται να «φάει» περισσότερα δολάρια από το προηγούμενο, και η ανοχή θα συνεχίσει να μεγαλώνει.
Σε 5 increments με 2% ο καθένας, ~10% του bank μπορεί να χαθεί ενώ κάθε ένα ξεχωριστά περνάει ως
NON_INFERIOR.

**Οδηγίες.** (1) Πρόσθεσε `min_effect_used: float` και `non_inferiority_margin_used: float` στο
`CompareResult`, στο CLI print και στο `results.json` (~10 γραμμές). (2) Απόφαση προϊόντος για τη
Φάση 2: είτε **κλείδωσε** το margin σε απόλυτο ποσό μία φορά (π.χ. `min_effect=400`, το επίπεδο του
v1d gate), είτε κράτα το ποσοστιαίο αλλά πρόσθεσε **σωρευτικό budget**: άθροισε τα αρνητικά
`mean_diff` όλων των αποδεκτών NON_INFERIOR increments και σταμάτα όταν ξεπεράσει π.χ. 2% του
τρέχοντος bank συνολικά, όχι ανά increment. Σήμερα το σωρευτικό είναι −$297 (μόνο το v1c), δηλαδή
υπάρχει περιθώριο — αλλά δεν παρακολουθείται πουθενά.
**Effort:** 30′ για το (1)· απόφαση + 1 ώρα για το (2).

### H2 — Το verdict αγνοεί εντελώς το paired win-rate: ένα increment που χάνει 86/96 episodes περνάει ως NON_INFERIOR  [CONFIRMED-EXEC]

Το `gate_v1c_holdout2` έδωσε: `wins_a=5, wins_b=43, episode_wins_a=10, episode_wins_b=86`,
`significant=True` με αρνητικό `mean_diff`. Δηλαδή το v1c είναι **στατιστικά βέβαιη** παλινδρόμηση
(t ≈ 9,2· CI ολόκληρο κάτω από το μηδέν, `[−362, −232]`) — απλώς μικρότερη από το margin των $773.

Το `CompareResult` **υπολογίζει** τα `wins_a/wins_b/episode_wins_*` και τα τυπώνει, αλλά η λογική
verdict στη [compare.py:395-419](harness/compare.py#L395-L419) δεν τα κοιτάει ποτέ. Ένα sign test σε
5-43 δίνει p ≈ 3×10⁻⁹ — σήμα πολύ πιο δυνατό από το $-verdict, που το πρωτόκολλο πετάει.

**Impact.** Το `NON_INFERIOR` διαβάζεται από τον αναγνώστη ως «δεν χειροτέρεψε». Στην πραγματικότητα
εδώ σημαίνει «χειροτέρεψε με βεβαιότητα, αλλά λιγότερο από το κατώφλι». Αυτά είναι δύο πολύ
διαφορετικά πράγματα για μια απόφαση GO, και το ένα μεταμφιέζεται σε άλλο.

**Οδηγίες.**
1. Χώρισε το `NON_INFERIOR` σε δύο τιμές: `NON_INFERIOR` (CI περιέχει το 0 — γνήσια ισοδυναμία) και
   **`WITHIN_MARGIN`** (CI ολόκληρο αρνητικό αλλά πάνω από `−margin` — βεβαιωμένη μικρή παλινδρόμηση).
   Το `go` να επιτρέπει το δεύτερο **μόνο** με ρητό `accept_within_margin=True`.
2. Πρόσθεσε binomial sign test στα per-seed wins και ένα πεδίο `sign_test_p`. Αν
   `wins_b > wins_a` με p < 0.01, μην επιτρέπεις `go=True` χωρίς ρητή παράκαμψη.
3. Το CLI να τυπώνει τη διάκριση ευδιάκριτα.

**Effort:** 2–3 ώρες (η λογική είναι τοπική· τα tests του `test_harness.py` για verdicts θα
χρειαστούν ενημέρωση).

### H6 — Στο parallel μονοπάτι, το `results.jsonl` γράφεται **μόνο αφού τελειώσουν όλα τα futures** — το `--resume` είναι πρακτικά no-op εκεί  [CONFIRMED-READ]

Το docstring υπόσχεται: «resume=True skips seeds already present in it, so a run that dies partway
(an errored seed, a crashed process) **can continue instead of restarting**». Στο sequential μονοπάτι
([compare.py:317-357](harness/compare.py#L317-L357)) το `_persist(row)` καλείται μετά από κάθε seed —
σωστά. Στο parallel ([compare.py:263-315](harness/compare.py#L263-L315)) όλα τα futures συλλέγονται
πρώτα μέσα στο `with ProcessPoolExecutor(...)`, και το `_persist` τρέχει **μετά** το κλείσιμο του
pool. Αν το run πεθάνει (Ctrl-C, OOM, reboot) στο 47ο από 48 seeds, το `results.jsonl` περιέχει μόνο
το meta line και χάνονται **και τα 47**.

Και το parallel είναι το **μοναδικό** μονοπάτι που χρησιμοποιείται για πραγματικά gates (workers=8) —
δηλαδή η δυνατότητα ανάκαμψης λείπει ακριβώς εκεί που κοστίζει (ένα 48-seed gate είναι ~2′ στα 8
workers αλλά ~10′ σε λιγότερα).

**Οδηγίες.** Μετακίνησε το finalize+persist **μέσα** στο `as_completed` loop, κρατώντας τη σειρά
εξόδου ανεπηρέαστη (το `sorted(computed)` στο τέλος ήδη το εγγυάται):

```python
for fut in as_completed(future_to_job):
    seed, swap = future_to_job[fut]
    ...store...
    if _seed_complete(seed):        # και οι 1-2 orientations έτοιμες
        row = _finalize(seed, orientations); computed[seed] = row; _persist(row)
```
Επιπλέον, το `job_errors` για ένα seed πρέπει να γράφεται μόλις **και τα δύο** orientations του
κριθούν (αλλιώς ένα πετυχημένο orientation πετιέται σιωπηλά — σήμερα ισχύει και είναι σωστό ως
πολιτική, αλλά αξίζει σχόλιο).

**Effort:** 1 ώρα + το υπάρχον `test_compare_workers_matches_sequential_per_seed_diffs` καλύπτει την
ισοδυναμία· πρόσθεσε ένα `test_compare_parallel_persists_incrementally`.

πρώτης ημέρας το σενάριο είναι απολύτως εφικτό: 2 sells + 2 seeds + 1 animal + 1 wheat + 1 land +

## 8. Δεύτερο pass — self-check του ίδιου του review

Ξαναδιάβασα τα ευρήματα με έμφαση στα gates v1c → v1d → v1e. Τι άλλαξε, τι απορρίφθηκε, τι
επαληθεύτηκε καθαρό:

**Αναβαθμίστηκε μετά το δεύτερο pass.** Το C1 αρχικά γράφτηκε ως High («το holdout κοιτάχτηκε δύο
φορές»). Ξαναδιαβάζοντας τα `runs/gate_v1c_*` με χρονολογική σειρά fingerprints, το πράγμα είναι
ποιοτικά χειρότερο: δεν είναι δύο ανεξάρτητες ματιές στο ίδιο κώδικα — είναι **επιλογή παραμέτρου
(`ne_carrot_tiles`) με κριτήριο το holdout αποτέλεσμα**, δηλωμένη ρητά μέσα στο ίδιο το
`agent/config.py`. Αυτό είναι ο ορισμός του «κράτα το max από k» και άρα Critical.

**Υποβαθμίστηκε.** Αρχικά είχα σημειώσει ως εύρημα ότι το `assign()` μπορεί να σκάσει με `TypeError`
συγκρίνοντας `Task` objects. Επαληθεύοντας το tuple layout, το ζεύγος `(unit_index, task.id)` στις
θέσεις 7-8 είναι **μοναδικό ανά candidate** (ένα candidate ανά (task, unit)), άρα ο 9-tuple πρόθεμα
δεν ισοβαθμεί ποτέ και το `Task` δεν συγκρίνεται ποτέ. Υποβαθμίστηκε σε **L2** (robustness).

**Απορρίφθηκε ως false positive #1.** Υπέθεσα ότι το `KAGGRI_ABLATION` θα ablate-άρει **και** το v1b
baseline, κάνοντας το criterion #1 self-test τετριμμένο (και άρα ολόκληρο το §1.5.2 άκυρο).
Ελέγχθηκε: `checkpoints/v1b/agent_checkpoint_v1b/config.py` δεν περιέχει καμία αναφορά σε
`KAGGRI_ABLATION` (grep = 0 hits). Το §1.5.2 self-test **ήταν** έγκυρο όταν έτρεξε. Ο κίνδυνος
υπάρχει μόνο **μπροστά**, για v1c+ baselines — καταγράφηκε ως H7 και ως προειδοποίηση μέσα στο H3(Α).

**Απορρίφθηκε ως false positive #2.** Υπέθεσα διπλοαγορά γης (BUY_LAND εκπέμπεται ξανά πριν το
`unlocked_quadrants` ενημερωθεί, όπως συμβαίνει με τα hands στο hour 0). Έλεγχος στο
[engine:689-701](engine_reference/kaggriculture.py#L689-L701): το `_do_buy_land` μεταλλάσσει το
`farm["unlocked_quadrants"]` **μέσα** στο `_process_market` του ίδιου step, οπότε η επόμενη
παρατήρηση το δείχνει. Δεν υπάρχει το lag που έχουν τα hands. Καθαρό.

**Απορρίφθηκε ως false positive #3.** Υπέθεσα crop-side production clipping (STRAWBERRY στο
`max_yield` να χάνει ticks όπως τα ζώα στο `max_held`). Έλεγχος στο
[engine:774-777](engine_reference/kaggriculture.py#L774-L777): το engine κάνει
`if production_count > cd["max_yield"]: continue` — **σταματά** την παραγωγή αντί να την κόβει, άρα
δεν υπάρχει σιωπηλή απώλεια. Το μόνο clipping μονοπάτι απαιτεί fertilizer bonus (+2), και ο agent δεν
εφαρμόζει ποτέ fertilizer (μόνο `COLLECT_FERTILIZER` και πώληση). Το `age >= 16` harvest είναι σωστό
για το pinned engine — παρέμεινε μόνο η **εύθραυστη σταθερά** ως M12.

**Επαληθεύτηκε καθαρό (μην ξαναψαχτεί).**
- **Αλυσίδα baselines των gates:** v1d vs `f0295e…` = v1b ✔ · v1c vs `6aecce…` = v1d ✔ ·
  v1e vs `f1e3ed…` = v1c ✔ · final vs `builtin:starter` ✔. Καμία σύγκριση με λάθος baseline.
- **Metric gate seat correctness:** το `compare()` διαβάζει `m0 = metrics0.get(0)` στο `A@0/B@1` και
  `m1 = metrics1.get(1)` στο `B@0/A@1` — δηλαδή πάντα το seat του `agent_a`, ποτέ του αντιπάλου.
  Καλύπτεται και από `test_compare_metrics_reads_agent_a_seat_in_each_orientation`.
- **Άθροιση αντί μέσου όρου** στα metric counters ανά orientation ([compare.py:237-243](harness/compare.py#L237-L243)) —
  σωστό και σκόπιμο· ένα defect σε ένα orientation δεν αραιώνεται.
- **`go` δεν μπορεί να είναι True με `INCOMPLETE`:** το `incomplete` υπερισχύει κάθε άλλου verdict
  ([compare.py:395-397](harness/compare.py#L395-L397)) και το `go` απαιτεί IMPROVED/NON_INFERIOR.
- **Καμία εγγραφή στο `results.jsonl` από worker** — το `_persist` είναι closure του parent και τα
  futures επιστρέφουν μόνο `(rewards, metrics)`. Το plan.md §1.5.1 (β) ισχύει για το jsonl (η
  ανακρίβεια αφορά μόνο τα replays, M7).
- **Ταξινόμηση κατά seed ανεξαρτήτως σειράς ολοκλήρωσης** (`sorted(computed)`) — το κριτήριο (i)
  του §1.5.1 δεν μπορεί να γίνει flaky από το completion order.
- **Determinism / seat isolation:** `_RUNTIME_BY_PLAYER` είναι keyed κατά `player` και μηδενίζεται σε
  `step == 0` ή `step < last_step`· τα `main.py` και `checkpoints/*/main.py` ζουν σε **ξεχωριστά
  package namespaces** (`agent` vs `agent_checkpoint_vX`), άρα μηδενικό cross-talk ακόμη και στη
  sequential in-process σύγκριση. Καλύπτεται από `test_g13_*`.
- **`animal_structure_ready` slot mapping:** `CONFIG["animals"]["targets"] = (COW, SHEEP, GOOSE)` →
  PASTURE slots `[(4,2), (3,2)]` για COW/SHEEP, COOP slot `[(3,0)]` για GOOSE. Το reasoning για την
  αποφυγή του κυκλικού BUY_LAND ↔ GOOSE dependency (COOP σε NW, όχι NE) είναι σωστό: αν το COOP
  καθόταν σε NE-locked γη, το `all(animal_placed(...))` gate δεν θα ικανοποιούνταν ποτέ και η γη δεν
  θα αγοραζόταν ποτέ. Καλά εντοπισμένο από το v1e.
- **Security:** το `pickle` χρησιμοποιείται **μόνο** ως `pickle.dumps` σε probe picklability
  ([compare.py:72-77](harness/compare.py#L72-L77)) — καμία deserialization μη-έμπιστου δεδομένου·
  ο `create_checkpoint` επικυρώνει το `version` με `^[A-Za-z][A-Za-z0-9_]*$` (κλείνει path traversal
  τύπου `../`)· `.env` untracked και εκτός index· κανένα secret/token/PII σε `results.json`,
  receipts ή replays (τα receipts περιέχουν μόνο step/pos/unit/action)· το `exec` του agent file
  είναι ίδιο με ό,τι κάνει το `kaggle_environments` και αφορά μόνο τοπικά, έμπιστα αρχεία.
  Το `main.py:8 sys.path.insert(0, "/kaggle_simulations/agent/")` είναι αδρανές τοπικά και σωστό
  στον server. **Καμία security ευπάθεια δεν βρέθηκε στο scope αυτού του review.**
- **Race conditions:** δεν υπάρχει shared mutable state ανάμεσα σε workers — κάθε job είναι ένα
  αυτοτελές `play()` με δικό του `env`, τα RNG seeds προέρχονται από το `configuration["seed"]` ανά
  episode (όχι από per-worker state), και τα replay filenames είναι μοναδικά ανά (seed, orientation).
  Τα ευρήματα H6/M9 αφορούν **ανθεκτικότητα** του pool, όχι race.
